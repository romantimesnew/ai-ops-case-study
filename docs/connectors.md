# Connectors: direct, free, auditable

Principle: an agent gets **its own direct API access** on its own machine, using scripts and official client libraries. No paid connector middleware and no browser automation for routine work.

Why:
- **Cost:** no subscription. The Google Cloud project needs no billing for these APIs.
- **Tokens:** an API call returns exactly the data needed. Clicking through a web UI burns far more agent quota.
- **Control:** I can see exactly which scopes were granted, and revoke them in one place.
- **Reliability:** the API has `validate_only` dry runs, while UI clicks don't.

## Google Ads API + GA4 (tested in production, Oct 2026)

1. **Cloud project.** Sign in with the Google account that has access to Ads and GA4. An organisation isn't required, and neither is billing. Create a project such as `<site>-ads-agent`.
2. **Enable APIs:** Google Ads API, Google Analytics Data API, Google Analytics Admin API.
3. **OAuth consent.** Audience *External*, app in testing mode. **Add the Google account as a test user.** Without that, sign-in fails with `403 access_denied` ("app not verified").
4. **OAuth client.** Type *Desktop app*. Download the client JSON. It travels as a file to the agent's machine and is stored in a private folder with `chmod 600`. It never goes in the repo or chat.
5. **Python venv** on the agent's machine. System pip is locked (PEP 668). Install `google-ads`, `google-analytics-data`, `google-analytics-admin`, `google-auth-oauthlib`.
6. **Consent flow.** `InstalledAppFlow` with a local redirect server, offline access and a forced consent prompt. Scopes: Ads, and Analytics edit + read-only. The agent opens the consent URL in its own browser, and **the human signs in** (2FA stays with the human). The refresh token is saved next to the client file, also `chmod 600`.
7. **IDs.** The Ads customer ID goes without dashes in the API. For GA4, use the *property* ID, not the account ID (a common mix-up).
8. **Access level.** The first Ads call failed with `CLOUD_PROJECT_NOT_APPROVED_FOR_PRODUCTION`. In my setup no developer token was needed; the Cloud project needed the **Explorer** access level (applied for on the Ads API page in Cloud Console, granted within minutes). Explorer has a daily operations cap and no Keyword Planner, billing or account creation, which is enough for auditing and managing one account.
9. **Operating rules baked into the agent profile:**
   - read and analyse without asking; audit first
   - any change: proposal (what, why, expected effect, risk) → owner's personal yes → `validate_only` → apply → re-read to verify
   - new campaigns are created **paused**
   - every applied change goes to `07-ads/changelog.md` with time, object ID, before → after, approver and verification

## Meta Marketing API (documented, not yet run)

Steps were checked against Meta's docs in Oct 2026: app via the *Create & manage ads* use case, linked to the business account; one system user; assign the app and ad account with the minimum task (`ANALYZE` for read-only); a system-user token generated by the human and handed to the agent as a file; `appsecret_proof` on calls; watch the usage headers for rate limits. Pixel and Conversions API are **site changes**, so they go through a card for the executor, not the ads agent.

## WordPress

- A **dedicated user for the executor** with the lowest role that works (editor), plus an **application password**. Never the admin account. Deleting things, plugins and security settings each need a separate card.
- **REST first.** Inventory (plugins, users, theme, pages) is read via the REST API with the application password. Clicks in wp-admin only with a stated reason and approval.
- **File mirror.** Custom code (mu-plugins) and the custom stylesheet are mirrored into `08-files/` of the repo, so the decision chat reads the real current code before writing a card. Core, plugins, themes, images, the database and config files are never mirrored.

## GitHub

The private repo is the shared memory. Agents read cards by path on `main`. The ads agent may commit only inside its own `07-ads/` folder and backlog rows. Shared rule files change only with owner approval.

## Secrets hygiene

- Secrets live only on the agent machine, in a private folder, mode 600. The repo documents **file names and where things live**, never values.
- Lead submissions, client emails and personal data are never committed.
- Reports never quote passwords or tokens, even partially.
